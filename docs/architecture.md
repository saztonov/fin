# Архитектура портала «КС»

Базовая реализация по корпстандарту v3.1 (single-VPS baseline). Keycloak, S3,
Sentry/мониторинг — этап 2; код им не противоречит (standalone auth §13,
хранилище за интерфейсом `lib/storage`).

## Компоненты

```
frontend (React + AntD6, Vite)  ──►  api (Fastify, 127.0.0.1:3000)
                                        │        │
                                        ▼        ▼
                               PostgreSQL   local storage (.data/uploads; S3 — этап 2)
                                        ▲        ▲
                                        │        │
                                     worker ──► parse-child (одноразовый процесс,
                                     (PG-jobs)   без секретов: разбор Excel)
```

- **api** — stateless HTTP: auth, справочники, грид КС-6, КС-2, приём файлов
  (file-guard), diff/apply импорта, экспорт Excel. Файлы НЕ разбирает.
- **worker** — опрашивает таблицу `jobs` (FOR UPDATE SKIP LOCKED, аренда,
  fencing token, retry c backoff, dead-state). Тип задач: `import_parse`.
- **parse-child** — spawn на каждую задачу: чистый env (без DATABASE_URL и
  секретов), SIGKILL по wall-clock таймауту, лимит stdout. Внутри — собственный
  потоковый ридер xlsx (zip + SAX) и распознавание листа: подбор листа, поиск
  шапки скорингом, словарь синонимов граф, разметка блоков периодов
  (см. import-format.md). exceljs остаётся только для экспорта.

## Модель данных

`construction_objects` ─* `estimate_parts` (части сметы). Договоров и ДС в портале
нет: смета, акты и импорт привязаны к объекту, а внутри объекта — к части сметы.
Структура сметы: `ks6_sections` (дерево, до 3 уровней) и `work_items`
(kind: `kvr` — агрегат, `nomenclature` — строка ввода; связь номенклатуры с её
КВР — по `kvr_item_id`, не по коду). Выполнение: `ks2_documents`
(draft/approved, unique номер **в части**) и `ks2_lines` (qty, amount).
Импорт: `import_files` + `import_staging` (payload разбора + summary).

**Части сметы (`estimate_parts`).** С 01.01.2026 ставка НДС 22 % вместо 20 %, и
заказчики ведут ведомость двумя листами. Часть — это версия сметы: `legacy` (единая
смета, ставка по дате — так живут все данные до появления частей) либо `vat20` /
`vat22` со своей ставкой. `ks6_sections`, `work_items`, `ks2_documents` и `ks2_lines`
привязаны к части (`part_id`); составные FK `(ks2_document_id, part_id)` и
`(work_item_id, part_id)` физически запрещают связать документ одной части с работой
другой. Контрольные суммы книги (`file_contract_total` / `file_executed_total` /
`file_totals_import_id`) живут на части: у листов 20 % и 22 % свои «Итого».

**Части НЕ складываются** — это перекрывающиеся версии одной сметы, а не слагаемые.
На `Сторис.xlsx` лист «КС6а 31.12.2025» несёт всю смету в ценах 20 % (6,95 млрд,
включая плановый график до мая 2028), лист «КС6а ндс22%» — пересчёт оставшегося
объёма по новой ставке (1,49 млрд), и ~2,5 тыс. номенклатур у них общие. Поэтому
грид всегда показывает одну часть, а карточка объекта — актуальную версию (старшая
по порядку вкладок) и подписывает её тегом. Смешивать непустую `legacy` с
`vat20`/`vat22` запрещено: сначала «Очистить смету».
Служебные: `users`, `refresh_tokens` (rotation + reuse detection), `audit_log`, `jobs`.

Деньги — `numeric(18,2)`, расценки — `numeric(18,6)`, количества — `numeric(15,6)`;
в коде ходят строками, вся арифметика в `lib/money.ts` (decimal, half-up как в Excel).
Значения ячеек Excel читаются исходным десятичным текстом, минуя double: `toFixed(2)`
округляет по представимости и на «половинке копейки» (0,615) уводит сумму вниз.
Soft delete через `deleted_at` с partial-unique индексами.

## Расчёты (ks6.service)

- Стоимость ручного ввода: `round2(qty × unit_price)`; импортированная история —
  суммы **как в файле** (не пересчитываются).
- «Выполнено с начала строительства» = Σ строк **утверждённых** КС-2; черновики
  видны в своих колонках, в виджеты не входят.
- КВР = Σ его номенклатур (стоимость); раздел = Σ вложенных номенклатур;
  Итого = Σ всех номенклатур. Строки `в т.ч.` (`kind = 'subline'`) не входят ни в одну
  сумму. «Остаток» = смета − выполнено (минус подсвечивается).
- НДС выделяется из суммы с НДС по ставке. **Ставка части главнее даты**: у `vat20`
  это 20 %, у `vat22` — 22 %, независимо от дат (смета 2023 года законно исполняется
  в 2026-м). Для `legacy` ставка по дате: 20 % до 31.12.2025, 22 % с 01.01.2026
  (таблица `vat_rates`) — для ячеек периодов по `period_from`, а для договорных
  колонок, у которых своего периода нет, берётся действующая на сегодня. Только при
  отображении/экспорте.
- Цена за единицу в режиме «без НДС» округляется **только при выводе** (`PriceText`,
  два знака): деление на (100 + ставка) даёт шесть знаков, которых в книге не было,
  а API продолжает отдавать точное значение — по нему живут экспорт и сверки.
- Итоговый НДС — **сумма построчных**, а не выделение от итога: только так «без НДС»
  по строкам складывается в «без НДС» по документу до копейки.
- Страница КС умеет показывать таблицу в двух видах: `GET /objects/:id/ks6?vat=net`
  отдаёт все суммы с выделенным НДС (грид, разделы, итоги; цена за единицу — делением,
  а не вычитанием округлённого НДС). Сумма каждого КС-2 приходит всегда валовой плюс
  `vatRate`/`vatAmount`/`netAmount` — панель КС-2 показывает все три независимо от режима.
- Договорные значения строк (`contract_total`) хранятся как в файле — копеечная
  совместимость с исходным Excel важнее пересчёта.
- Цена за единицу — `numeric(18,6)`: в ведомостях расценка почти всегда с 4–6 знаками,
  и урезание до копеек ломало бы `qty × price` при ручном вводе КС-2.
- Расхождения с исходной книгой видны в гриде постоянно: ячейка обводится красным,
  подсказка называет сумму из файла и разницу. Сверяются «Всего» против `qty × price`,
  Σ номенклатур против «Итого» книги, выполнение строки и итога против контрольной
  графы «Выполнено с нач. ст-ва». Контрольные суммы книги — снимок последнего
  применённого импорта (`estimate_parts.file_*`, `work_items.file_executed_total`).
  Выполнение сверяется только по КС-2 с `source = 'import'`: документы, введённые
  вручную, законно уводят сумму от книги. Допуск подсветки — 0 коп.

Нарастающие итоги считаются на лету (≤ ~300 строк × ~20 периодов) — materialized
view не нужен.

## Аутентификация (standalone, этап 1)

Регистрация → `is_active=false` → активация админом. Вход: access JWT (HS256,
15 мин) + opaque refresh в httpOnly cookie (`SameSite=Strict`,
path=/api/v1/auth, 30 дней), rotation при каждом refresh, reuse detection
(повторное предъявление использованного токена гасит всё семейство + audit).
CSRF-дисциплина cookie-эндпоинтов: обязательный заголовок `x-requested-with`.
Клиент держит access только в памяти и дедуплицирует параллельные refresh.
Финальная авторизация — на сервере: RBAC-плагин + object-scope guard
(экономист без назначений видит все объекты — требование заказчика).

## Наблюдаемость и эксплуатация

pino JSON-логи с redaction (authorization/cookie/password/token),
`/health/live` + `/health/ready` (ping БД), graceful shutdown, rate-limit
(общий + жёстче на auth), helmet-заголовки, request-id. Production startup
checks (config.ts): плейсхолдеры секретов и отсутствие TLS БД валят старт.
Деплой: immutable-образ (backend/Dockerfile: api|worker|migrate), миграции —
отдельный шаг, лимиты контейнеров в deploy/docker-compose.yml.
